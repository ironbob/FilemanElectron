# 列表视图拖拽「无反应」：元数据列被误划为框选背景

## 现象

列表视图抓取文件行拖动，大部分落点完全没有拖拽反馈（不出现拖拽图像、
不进入放置流程），偶发变成框选。用户感知为「拖动坏了」。

## 排查（instrumented 实测，非读码推测）

用 Playwright `_electron` 拉起**真实应用**（非 e2e mock——mock 的 Proxy 会把
`supportsNativeDrag` 变成函数，`=== true` 判 false，原生分支天然关闭，
e2e 永远测不到这条链路），埋点 document capture 阶段
`pointerdown/mousedown/dragstart`，再用 CDP 真实鼠标手势逐位置探测：

| 起拖位置（list 行） | dragstart | 结果 |
|---|---|---|
| 图标 | ✅ | 原生接管全链路通（session begin → IPC → main `startDrag invoked`） |
| 文件名 | ✅ | 同上 |
| 行左 padding / 列间隙 / 日期/大小/种类/权限列 | ❌ | 被路由进框选，`preventDefault` 吞掉 dragstart |
| grid 格子 | ✅ | 正常（格子整体是热点） |

结论：**原生拖拽链路本身健康**（`startDrag` 正常调用、自定义图标正常生成），
死因是 `ae16fc2` 的热点收窄——「仅图标+文件名可拖、元数据列视为框选背景」。
双面板窄行（~581px）下热点仅占行宽约三成，随手抓行大概率落进死区。

### Finder 语义澄清

真实 Finder 列表视图**从元数据列（日期/大小/种类）同样能拖动文件**；
框选只在「行后空白区」发起。ae16fc2 对 Finder 的引用有误。

### 附带发现（排查中排除的嫌疑）

- `4438534` 之后的提交（4d92a51/ccd2c00）零改动拖拽链路（逐 diff 核对）；
- `out/` 产物与源码一致（22:57 全量重建）；
- grid 视图、drop 侧（extractDragSource/queueTransfer）均完好；
- CDP 合成输入**无法驱动 OS 级原生拖拽会话**（startDrag 之后合成 mouse move
  不产生 dragover/drop）——原生会话的窗口内放置只能真人手势验证，自动化
  排查时不要把「合成手势下无 dragover」误判为回归。

## 修复（2026-08-17）

行内**全部内容恢复为拖拽热点**；框选起点改由新增的**行尾固定留白**
`finder-rubber-tail`（`w-12 self-stretch`，视觉即 Finder 的行后空白区）承担：

- `handleContainerMouseDown` 路由改为 `!onFileItem || onRubberTail` 才框选；
- 删除已无路由语义的 `finder-drag-hotspot` class（图标/文件名两处）；
- 行尾留白固定 48px，行填满视口时框选仍有保证起点——ae16fc2 要解决的
  问题不回潮；表头/列表下方空白仍可发起框选；grid 行为零改动。

## 验证

- 四点矩阵实测（真实应用）：图标/文件名/元数据 → `dragstart (native takeover)`
  + main `startDrag invoked`；行尾留白 → 框选矩形出现、无 dragstart。
- `npm run typecheck` 干净；drag-transfer e2e 5/5；
  quick-look 2 个失败为改动前即存在（stash 对照复跑确认，属既有基线）。

## 遗留

- columns 视图行从不支持拖拽（历史上无 draggable），如需补另行处理；
- 原生会话「窗口内 dragover/drop」依赖 4438534 的手动验证结论
  （macOS 不受 electron#7118 Windows 限制影响），若真人实测拖回本窗口
  仍无放置反馈，先看 DevTools 是否有 `[DnD][App] pane drop` 日志再定位。
